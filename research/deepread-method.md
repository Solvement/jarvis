# 精读方法 · 持续修订

从每次精读讨论里提炼。目标：下一篇精读一次写对，少返工。

## 读者画像（2026-09-06 起）
- 已掌握：Agent、RAG、Agent Skills 的格式（SKILL.md、根/子 skill、progressive disclosure）。这些不用讲，讲了是浪费读者时间。
- 读法：分段读，读到一处不懂就停下来问，要求「究竟怎么做、怎么判断」。
- 目标：能给别人讲；因此每个机制都要能回答「谁做、输入什么、做什么、输出什么、怎么算做完」。

## 写法规则（来自第一篇的返工）
1. **先给「核心两半」**：一篇论文通常有「方法」和「证据」两半，开头一句话要把两半都点到，并说清读者关心的那一半占多大比例（例：四个基准里三个用的是任务导向蒸馏，不是仓库蒸馏）。
2. **机制段落用五要素**：执行者、输入、动作、输出、判定标准。缺任何一个，读者就会问「究竟怎么做」。
3. **抽象流程配一个真实产物**：不要只画流程图。去仓库里找一次真实运行留下的文件（例：huggingface_hub 的 test-cases 和 verification-report.json），把原文贴出来讲。
4. **「验证」类主张必须给结果分类表**：什么算通过、什么算失败、哪种失败才是方法本身的错。
5. **术语层按读者画像裁剪**：读者已知的概念不解释；论文自造的词第一次出现就用大白话 + 与相近概念的区别。
6. **可视化服务于「讲给别人」**：流程图要能直接当板书；每张图配「怎么看」。
7. **先具体后抽象**：先走一个例子，再给形式化符号。

## 表达形式（2026-10-04 用户指定，关键，生成每篇精读都要遵守）

依据：用户转述的 Karpathy 观点——把模型输出转换成人更容易理解和验证的形式；不要让读者线性读完所有文字。「可丢弃软件」成本接近零，按读者知识水平临时生成，用完可丢。

按难点类型选形式，不要求每篇四种全做：

| 难点来自 | 用什么 | 收益 |
|---|---|---|
| 语言噪声：长句、抽象词、同一概念绕很多字 | **文字按 ASD-STE100 风格约束**（用户原话「80% 的 ASD-STE100 风格」）：短句、一句一个意思、明确主语和动作、术语全文一致、含义唯一 | 减少歧义，便于逐句检查 |
| 关系复杂：架构、调用链、因果、模块依赖 | **图表**：流程图、架构图、概念图 | 一眼看到节点怎么连、数据怎么流、哪里会断 |
| 状态、参数、动态变化 | **交互网页**：按钮、滑块、动画，改参数看结果 | 把「读结论」变成「亲手验证」 |
| 时间顺序：算法执行、逐步推导、抽象过程 | **解释视频**（3Blue1Brown 风格：动画 + 旁白 + 重点标注） | 建立直觉 |

执行要求：
- 先判断这一节的难点属于哪一类，再选形式；文字永远存在，图/交互/视频是加在难点上的。
- 交互和视频只验证它编码的规则，要标明简化假设，不冒充复现或真实系统测试。
- 证据、来源定位、阅读版本不可丢；可丢的是演示界面。
- 与 `state/editorial-preferences.md`（2026-10-03）同源，冲突时以本节为准。

## 讨论流程
- 读者读到哪里停、问什么、我怎么答、读者确认什么，记在该篇的 `discussion.md`。
- 讨论结束后统一改精读稿，而不是边讨论边改。
- 每轮讨论后回到本文件，看有没有新的写法规则。

## 阅读产品反馈 · 2026-10-19（新版流程尚待样章验证）

用户明确：精读正文应帮助自己快速理解原文的重要内容，而不只是五六句摘要。辅助问答用于阅读正文或原文时解释不懂的概念，不应承担整篇精读的主要呈现。当前小对话框偏窄、快速输出和大量引用链接影响阅读；依据要可追溯，但不需要默认把源文编号与完整链接铺在主文或回答中。

参考站论文详情中的 Explain This Paper 入口位于 Academy Studio，链接预填 interactive lesson 的问题、核心思路、机制、结果与知识检查，并携带 learn/web-search 能力参数。本次实际访问跳转登录，只确认公开入口与交接，未确认其登录后产物或质量。证据保存在 output/dair-builder/。

用户希望本站提供自己的选题、解释与判断，能够区分贡献类型、工程机制和模型能力；纯粹转载 HF/GitHub 榜单或把任务转给站外 ChatGPT 不能成为核心价值。当前项目三榜仍按上一轮要求只展示中性介绍，等待用户表达兴趣，不据本轮讨论自动选择项目。

候选方向：先完成一篇可连续阅读的真实精读样章，以读者是否理解方法、证据和限制验收，再决定界面与批量流程。

**推理**：原文可检索只说明有材料，回答能引用只说明可追溯；这些不能证明讲解覆盖完整、概念顺序正确或解释足够。用户需要的是经过组织、核对、保存和修订的阅读作品。

**理由**：正文以连续例子贯穿问题、方法和证据，难点配必要的图示；辅助问答携带所选段落与文章背景，只解决局部疑问。引用默认收起，仍能按需检查原文。评估必须检查实际成品，不以字数、格式完整或“生成成功”认证质量。

**对比**：加长摘要会增加文字而不保证机制解释；长聊天不容易形成稳定正文与修订版本；仅站外预填 prompt 会分散产物和阅读上下文。站外工具可以是补充入口，核心内容仍需本站有明确覆盖与审校的成稿。

**风险**：讲解流畅可能掩盖错误、遗漏和作者结论的限制；简化例子也可能改变关键条件。核心主张必须回原文复核，未知部分明确列出；交互演示不当成原实验，未经运行的模型或项目结果不称本机验证。idea/工程/模型是贡献方向，solid 对应证据支撑程度，不能简单排列成高低等级。本节记录用户偏好与待验证方案，不表示已实现新的精读流水线或已经交付合格样章。

## 从最小问题长出设计 · 2026-10-19T17:27:11-04:00

用户确认希望采用类似系统设计的解释顺序：先看最小问题与一条输入到输出的链路，再看业务或研究约束如何增加，每引入一个机制都解释它填补上一步的哪个缺口。以连续正文展开，避免先列完整架构再逐个解释名词。用户已授权自行选择一篇HF论文和一个项目试写，取代上一阶段的等待选题。

已实施样章：PagedAttention v1 与 ContextMode 固定commit，分别9/10节；选题、实际覆盖、论断、图示及原始验证见authoring/samples/2026-10-19与D-028。本文的重建顺序是教学因果，不声称作者按该时间顺序开发。主文引用收起，问答辅助局部概念；用真实材料和受控实测说明机制及反例。

验收仍由读者的实际理解来推进：是否能复述组件必要性、状态变化、成立条件和失效情况；长文、结构校验与一次成功实验不等于已经讲好。先评价样章，不自动把同一写法批量应用于所有论文、模型或项目。

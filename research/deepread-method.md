# 精读方法 · 持续修订

从每次精读讨论里提炼。目标：下一篇精读一次写对，少返工。

## 读者画像（2026-09-06 起）
- 已掌握：Agent、RAG、Agent Skills 的格式（SKILL.md、根/子 skill、progressive disclosure）。这些不用讲，讲了是浪费读者时间。
- 读法：分段读，读到一处不懂就停下来问，要求「究竟怎么做、怎么判断」。
- 目标：能给别人讲；因此每个机制都要能回答「谁做、输入什么、做什么、输出什么、怎么算做完」。

## 写法规则（来自第一篇的返工）
1. **先给「核心两半」**：一篇论文通常有「方法」和「证据」两半，开头一句话要把两半都点到，并说清读者关心的那一半占多大比例（例：四个基准里三个用的是任务导向蒸馏，不是仓库蒸馏）。
2. **机制段落用五要素**：执行者、输入、动作、输出、判定标准。缺任何一个，读者就会问「究竟怎么做」。
3. **抽象流程配一个真实产物**：不要只画流程图。去仓库里找一次真实运行留下的文件（例：huggingface_hub 的 test-cases 和 verification-report.json），把原文贴出来讲。
4. **「验证」类主张必须给结果分类表**：什么算通过、什么算失败、哪种失败才是方法本身的错。
5. **术语层按读者画像裁剪**：读者已知的概念不解释；论文自造的词第一次出现就用大白话 + 与相近概念的区别。
6. **可视化服务于「讲给别人」**：流程图要能直接当板书；每张图配「怎么看」。
7. **先具体后抽象**：先走一个例子，再给形式化符号。

## 表达形式（2026-10-04 用户指定，关键，生成每篇精读都要遵守）

依据：用户转述的 Karpathy 观点——把模型输出转换成人更容易理解和验证的形式；不要让读者线性读完所有文字。「可丢弃软件」成本接近零，按读者知识水平临时生成，用完可丢。

按难点类型选形式，不要求每篇四种全做：

| 难点来自 | 用什么 | 收益 |
|---|---|---|
| 语言噪声：长句、抽象词、同一概念绕很多字 | **文字按 ASD-STE100 风格约束**（用户原话「80% 的 ASD-STE100 风格」）：短句、一句一个意思、明确主语和动作、术语全文一致、含义唯一 | 减少歧义，便于逐句检查 |
| 关系复杂：架构、调用链、因果、模块依赖 | **图表**：流程图、架构图、概念图 | 一眼看到节点怎么连、数据怎么流、哪里会断 |
| 状态、参数、动态变化 | **交互网页**：按钮、滑块、动画，改参数看结果 | 把「读结论」变成「亲手验证」 |
| 时间顺序：算法执行、逐步推导、抽象过程 | **解释视频**（3Blue1Brown 风格：动画 + 旁白 + 重点标注） | 建立直觉 |

执行要求：
- 先判断这一节的难点属于哪一类，再选形式；文字永远存在，图/交互/视频是加在难点上的。
- 交互和视频只验证它编码的规则，要标明简化假设，不冒充复现或真实系统测试。
- 证据、来源定位、阅读版本不可丢；可丢的是演示界面。
- 与 `state/editorial-preferences.md`（2026-10-03）同源，冲突时以本节为准。

## 讨论流程
- 读者读到哪里停、问什么、我怎么答、读者确认什么，记在该篇的 `discussion.md`。
- 讨论结束后统一改精读稿，而不是边讨论边改。
- 每轮讨论后回到本文件，看有没有新的写法规则。

# 精读标准

目标：读完能够准确复述、给别人讲懂，并能质疑、比较、迁移。长度和章节数量都不构成充分条件。

## 三种文章承担不同任务

1. 摘要解读：项目依据 README 和相关介绍，论文依据 abstract；交代问题、方法轮廓、价值、证据性质、成本与不适用边界，信息足以决定是否值得精读。明确尚未读透源码或正文。
2. 工具/skill 选用指南：逐个说明解决什么问题、什么情境使用、输入输出、前提与边界；给出选用路线与容易混淆的比较。工具机制确实有研究价值时，再单独精读。
3. 精读：项目追踪实际代码、入口、核心数据、主链路、模块职责、关键决策、修改影响和失败模式；论文追踪原文、问题来源、假设、方法步骤、公式含义、实验设计、强基线、消融、适用条件和未证实之处。不能把 README 或 abstract 扩写后标成精读。

## 正文组织

从一个具体问题进入，采用一个连续例子带读者走过主要机制。先建立问题和概念，再使用专业术语和公式；类比同时说明失效边界。细节写清楚，但不把文章变成符号或文件清单。

解释它如何做、为什么做、解决什么问题、问题为何存在、替代设计的利弊。关键机制要追踪到实际实现或原文推导，重要分支、参数、边界和信息流不得压成泛泛两句话。没有读到的地方列入覆盖缺口，不凭项目宣传补全。

自己的分析必须独立出现：对比邻近方法、旧判断到新判断、可迁移思路、版本变化、与既有阅读的关联。源头事实、源码核查、作者实验、个人推断和应用建议分别标明。没有运行或复现，不称运行验证或实验结论。

## 验收与存储

固定源码 commit 或论文版本；逐项记录已读、浏览、未读及原因。关键论断定位到函数、原文节、公式、表或实验条件；机制保存 3–6 步实现过程和适用边界。复核要检查无证据论断、覆盖遗漏、过度压缩、误导性概括和前后矛盾。结构校验只是入库约束，不能自动证明精读质量。

状态为 draft → needs_review → accepted_main_text（明确专题范围）→ accepted。专题通过不代表整个项目或论文已全面验收；历史文章未补齐证据记录时显示待复核，保留原文。

三层沉淀：冷存保存实际引用的源文和 PIN；脑图保存元数据、论断、机制、关联和开放问题；Outputs 保存人读的正文。追加修订版本，保留旧判断与修订依据。网站保存版本，读者可导出文章；本地 reading-vault 保存三层记录。新概念第二次出现时再建公共概念页，避免每篇制造孤立词条。

论文标题旁显示作者；机构名称只来自论文首页或作者官方来源，不能由 HF 上传者、语言或仓库归属推断。不要替用户标记“已读”“已懂”，也不因一篇文章自动改写个人知识画像。

## 发现范围（2026-10-03 用户调整）

GitHub 日周月榜保持完整。HF 日周月各展示、处理来源前 5 篇，保持原始顺序和跨榜重复；来源完整快照仍可保留供回查。停止处理范围外摘要积压。精读推荐每天 0–2 篇，允许没有推荐，候选推荐不代表精读已经完成。未复核的历史文章留在书架，不自动充当今日推荐。来源尚未更新时显示来源实际日期，不把刷新日期当成论文榜单日期。
